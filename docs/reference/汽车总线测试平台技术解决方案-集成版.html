项目概述与需求演进

1.1 项目背景

随着汽车电子电气架构（EEA）向域集中式演进，整车 CAN / LIN / CAN FD / CAN XL 总线网络复杂度持续攀升。研发与测试环节迫切需要一套集总线监控、剩余总线仿真、诊断、自动化测试、测试与缺陷工程管理于一体的测试平台，用于 ECU 开发验证、整车网络联调、协议一致性测试与量产质量管控。

本方案对标业界标杆 Vector CANoe（含 vTESTstudio、TFS、Test Report Viewer 三件套）与 Polarion / TestRail / Jira 等工程管理工具，结合自有硬件实现"硬件 + 软件 + 测试工程"一体化交付，目标是以约 1/100 的成本实现 90% 以上的核心工作流覆盖。

硬件平台设计

4.1 总体方案：FPGA + MCU 双核架构

对标 Vector VN1630A（4 通道 CAN/FD）与 VN8900 系列架构，采用 FPGA + MCU 双核架构：FPGA 承担所有时间关键型任务（时间戳、过滤、注入、采样、同步），MCU 承担协议处理、调度表执行与 USB 传输。该架构与 CANoe 硬件（内部 FPGA/ASIC）同构，是"接近 CANoe"的硬件基础。

4.4 USB 高速链路设计

  • 接口：USB3300 ULPI PHY + STM32H750 OTG HS 控制器，480Mbps。
  • 端点规划：EP1 Bulk IN（数据流，1024B 多包）、EP2 Bulk OUT（命令/发送）、EP3 Interrupt IN（事件/错误通知）。
  • 带宽核算：4×CAN FD 满负载约 4×8Mbit/s=4MB/s 净荷 + 协议头，480Mbps 链路理论 60MB/s，余量约 2.3 倍，支持 8 通道全速采集。
  • 批量模式：批量解析 16 帧/包，MMAP 零拷贝 + 双缓冲，规避小包中断风暴。
  • 固件升级：DFU 模式 + 双 Bank OTA，掉电安全。

6.3 剩余总线仿真引擎（RBS）

  • 确定性事件循环：1ms 基准时隙 + 高精度补偿，保证调度表帧时隙确定性。
  • 调度表驱动：LDF/CAN 矩阵调度表解析执行，支持周期/事件/突发三种发送模式。
  • 节点行为模型：Python 定义信号处理逻辑（状态机、抖动、故障注入），与仿真节点分离。
  • 交互式生成器（IG）：手动拖拽信号值即时改变发送帧内容，运行中动态启停。
  • 混合模式：回放（Replay）与仿真叠加——在录制日志上"接入"虚拟节点，复现现场。
  • 故障注入：信号超差、帧丢失、错误帧、总线关断，供负向测试用例使用。

# CAPL 兼容示例：CAPL 代码与 Python DSL 语义对齐 /* CAPL 原始代码 */ on message EngineData_01 { if (this.RPM > 3000) output(this); } # Python DSL 等价实现 @on_message("EngineData_01") def handle(msg): if msg.signals["RPM"] > 3000: bus.send(msg) log.info(f"RPM overrun: {msg.signals['RPM']}")

  • 转换工具链：.can 存量工程导入器（解析 CAPL → 生成 Python，规划）。
